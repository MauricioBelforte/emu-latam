# Log: Integración GGPO + Sistema P2P

**Fecha:** 2026-07-24
**Tipo:** Integración
**Componente:** 18-P2P-Propio

## Descripción
Se integró el motor GGPO (fcadefbneo) con el sistema P2P propio. Ahora cuando `engine === "ggpo"` y el método de reto es `"p2p"`, el flujo descubre IPs via P2P y lanza GGPO directamente (en lugar de RetroArch).

## Cambios Realizados

### `client/src/context/ChallengeContext.tsx`

**Código original:**
- `acceptChallenge()` (guest): Solo manejaba RetroArch para P2P (LAN → `launch-game`, WAN → `connection_confirmed` + `launch-game`)
- ACCEPT handler (host): Solo manejaba RetroArch para P2P (`launch-game` + `p2p-host-register-guest` + `publishP2pConnectionConfirmed`)

**Código nuevo:**
- `acceptChallenge()` (guest): Agrega rama `if (engine === "ggpo")` después de `p2p-guest` — detecta IP propia y envía ACCEPT con `guestIp` (no lanza nada, espera connection_info)
- ACCEPT handler (host): Agrega rama `if (engine === "ggpo")` al inicio del bloque P2P — detecta IP propia y envía connection_info con `ggpoHostIp` (no lanza RA ni registra guest)

**Archivos modificados:**
- `client/src/context/ChallengeContext.tsx` — Líneas 161-168 (guest), 241-253 (host)

## Flujo Resultante

```
Host (P2P+GGPO)               Guest (P2P+GGPO)
|-- p2p-host                  |
|-- send challenge(candidate) |
|                              |-- p2p-guest(candidate)
|                              |-- get-lan-ip → ACCEPT(guestIp)
|<- ACCEPT(guestIp)           |
|-- get-lan-ip → conn_info    |
|                              |<- conn_info(ggpoHostIp)
|                              |-- ggpo-launch(P1, hostIp)
|                              |-- guest_ready(guestIp)
|<- guest_ready(guestIp)      |
|-- ggpo-launch(P0, guestIp)  |
```

Los handlers existentes `connection_info` y `guest_ready` no se modificaron.
